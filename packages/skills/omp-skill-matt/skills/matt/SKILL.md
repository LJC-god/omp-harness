# Matt

Matt is an engineering method library, not an agent or controller. Sol selects the relevant capability and assigns its use to the owning author for the current complex engineering phase. A clear user request or retained authorization is sufficient; no prior PM document or machine-readable handoff is required. Routine small work skips Matt unless explicitly requested.

Matt does not turn an underspecified complete-product brief into an engineering interview or replace Sol's compact product-discovery pass. Use it after Sol has frozen the first useful journey, boundaries and the engineering question. Technical API, version, compatibility and component facts that could change that decision go to Sol's existing targeted Web route; do not create a research side workflow.

## Select the current phase

- Complex feature decomposition or unclear implementation path: `references/flow.md`.
- Implementation with meaningful behavior tests, difficult debugging or requested code review: `references/build-and-verify.md`.
- Module design, substantial refactoring or another specific maintenance question: `references/maintenance.md`.

Read one matching reference and its selected official leaf from `SKILL_UNAVAILABLE (skills upstream leaf is not shipped)`. Use the relevant engineering method; do not preload the full library or run a default interview/spec/ticket/review chain. Record the selected method in the existing assignment/checkpoint when useful. No separate tracking system.

## OMP integration boundaries

The local orchestration rules and current user instructions take precedence over imported setup, model choice, delegation and approval sequences. Do not run setup-matt-pocock-skills merely because this is a new repository, change global configuration, create mandatory tickets, or add dual reviews. Do not send a clear engineering task back to PM to fill missing template fields. Ask only about consequential missing choices; make reversible engineering assumptions within authorized scope and retain relevant evidence.

Sol owns coordination and verification decisions. Kimi/frontend-worker authors initial frontend source, including prototypes; GPT performs the applicable screenshot review. A confirmed post-implementation defect transfers to repair-worker after the initial author settles, while an interrupted initial implementation remains with its author. Other product/software artifacts follow the existing assigned native/controlled route. Method selection never authorizes Sol implementation. Reuse current verification and preserve frozen controlled-run requirements. Return implementation and evidence, not another approval request.

For current API, version and compatibility facts, Sol uses the shared web research route; clear supplied requirements and local code analysis do not need Web retrieval. Workers return WEB_RESEARCH_REQUIRED with the precise question and continue independent work; they do not spawn another research workflow. Link a design conclusion or gap to actual current-branch receipts with `omp_research_evidence` when useful, while keeping user/model synthesis distinct from runtime retrieval. Existing stack, authorization and source ownership remain in force.
