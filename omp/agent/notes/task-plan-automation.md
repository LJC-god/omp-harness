# Task-plan automation entry

`task-plan-automation.ts` is a plan runner. Root approves a local plan and the user or a coordinator acting under existing user authorization explicitly invokes it; it does not replace the existing manual controller workflow. The core still does not create worktrees or dispatch authors by itself. For complete products, product-planning.md selects this entry after interfaces, path ownership and dependencies are settled; the coordinator can invoke it under existing implementation authorization. The entry on this machine is <repo>/scripts/task-plan-automation.ts. Validate the plan first; do not use normal mode on an occupied or dirty target. Its concurrent author dispatch accepts 1 through 4 and defaults to 4; it is distinct from the native per-session ceiling and controller leases.

Each attempt retains task-progress.md with a task table and dependency diagram, planned branch/worktree paths, receipt-based state and an explicit acceptance limitation. This execution diagram complements the module diagram in the parent product plan; it is not an inferred architecture. Plan JSON has `target`, `tasks`, `finalTestCommand`, optional `candidateSetupCommand`, and optional `executionPolicy`; the runner defaults a new plan to `integration-v1` and passes that policy to `run_begin`. `candidateSetupCommand` is an argv string array, never a shell string. Missing-command auto-detection is bounded to root `package.json` dependencies/workspaces and tracked root JavaScript lockfiles; other package layouts or ecosystems must explicitly supply a project-approved command, with no automatic package-manager selection or claim of universal dependency detection. The command is required when that bounded detection finds a dependency-bearing candidate and runs only in the merged candidate's actual cwd, immediately before its frozen candidate check; a dependency-free candidate records an explicit skipped setup receipt instead. A missing required command fails closed. The setup receipt is independent from the candidate/project check, and neither receives an automatic retry. A task supplies `id`, `writePaths`, `sharedResources`, `dependsOn`, `prompt`, `testCommand`, and optional existing writing `agent` (default `task`; accepted: `task`, `sonic`, `frontend-worker`, `fast-worker`, or `repair-worker`). Commands are argv arrays, never shell strings. The runner validates strict fields, bounded input, graph scopes, D-drive Git identity, clean target/ref, and changed paths before staging exactly those paths.

Use:

```powershell
bun <repo>/scripts/task-plan-automation.ts validate D:/plans/example.json --lab-root D:/Labs/omp/omp-automation-lab-20260918
bun <repo>/scripts/task-plan-automation.ts run D:/plans/example.json --lab-root D:/Labs/omp/omp-automation-lab-20260918 --concurrency 4
bun <repo>/scripts/task-plan-automation.ts validate D:/plans/example.json --normal
bun <repo>/scripts/task-plan-automation.ts run D:/plans/example.json --normal --concurrency 4
bun <repo>/scripts/task-plan-automation.ts inspect D:/Labs/omp/omp-automation-lab-20260918/automation/attempts/<attempt-id>
```

`inspect` reads the saved attempt mode and needs no mode flag. In lab mode the plan target must be inside the marked lab root. The D lab must contain `.omp-automation-lab-root` with `omp-automation-lab/v1`. A minimal non-UI plan is:

```json
{
  "target": { "repo": "D:/Labs/omp/omp-automation-lab-20260918/projects/example", "ref": "main" },
  "candidateSetupCommand": ["bun", "install", "--frozen-lockfile"],
  "tasks": [{
    "id": "api", "writePaths": ["src/api.ts"], "sharedResources": [], "dependsOn": [],
    "prompt": "Implement the approved API change.",
    "testCommand": ["bun", "test", "test/api.test.ts"], "agent": "task"
  }],
  "finalTestCommand": ["bun", "test"]
}
```

Lab mode binds an explicit D control DB and applies a temporary configured overlay only to that root-session invocation. Normal mode keeps existing global role/model configuration and rejects an ambient lab environment. Neither mode falls back between databases; each attempt records mode, DB, a timestamp, runner/controller/task-graph/config/plan/prompt hashes, and a durable controller-receipt ledger. UI authors retain their frontend model route, including in lab mode; the temporary lab overlay applies only to the named non-UI and review roles. The automated `integration_check` covers only assigned branch/integration checks; legacy runs retain their frozen gates. Neither is full product or UI acceptance. The parent must obtain its own current-source red security-reviewer, blue verifier, purple-reviewer and applicable visual/experience receipts after integration; runner output explicitly leaves product acceptance pending.

Every new `integration-v1` runner context freezes `diagnosticEvidence` as `{ "schema": "omp-check-diagnostic/v1", "root": "<attempt>/diagnostics" }`. The controller requires an existing direct D: root outside the checked source tree, derives an immutable per-check JSON filename, and records only actual path, attempted path, SHA-256, status, truncation/gap/missing state and process metadata in its receipt. The file contains a bounded sanitized failure summary; it is not a general log. It drains and hashes the full raw stream, but runs a bounded-state UTF-8 redactor before retaining its 24 KiB sanitized head and 40 KiB sanitized tail. Recognized quoted JSON `token`, `access_token`, `id_token`, and `authorization` values plus Bearer values are redacted across pipe chunks and retained cuts; no fixed tail skip is used. `bytes`/`sha256` and `rawGap*` describe raw input, while `sanitizedBytes`, `sanitizedRetainedBytes`, `gap`, and `gapBytes` describe stored sanitized content. A noisy command still runs to completion: these storage limits never alter its execution result. The sanitizer cannot recognize arbitrary secret formats or recover sanitized content omitted from the middle, so commands must not print secrets. An absent failed write reports `path: null`, its intended location as `attemptedPath`, and `missing: true`; a partial regular file retains its actual path/hash but remains `write_failed` and unusable. Missing, write-failed, stream-failed, cancelled, timed-out, tampered, or path-invalid evidence cannot establish check completion; the raw process exit/cancellation state remains separate. Existing frozen contracts without this policy retain their historical behavior. Do not resume a new-policy run with an older controller: preserve its DB and diagnostic files for inspection, then settle it with compatible code; never clear, relabel, or rewrite it as legacy.

Legacy attempts retain their task-ID-sorted ready waves and wait for all launched authors before ordered integration; their receipts are historical execution facts, not evidence of continuous refill. New runner plans default to `executionPolicy: "integration-v1"`, so the runner maintains at most four active authors and refills a free slot with the next dependency-ready, non-conflicting task after its predecessor settles; integration remains serialized. Do not launch concurrent runners to multiply the writing limit. A failed author, `integration_check`, or merge pauses new dispatch and preserves worktrees, raw command evidence, receipts, and `failure.json`; it performs no retry, reset, cleanup, recovery, or resume. After running tasks drain, the runner may reconcile only this attempt's newly acquired claim whose admission raced the failure latch and whose author was never dispatched, if the controller proves there is no author receipt or active writer and the branch and head are clean and unchanged; it cancels that unused claim and retains the evidence. It never auto-reconciles started or unknown execution. Only Sol may resume an inspected, proven-independent package. `integration-v1` is unavailable to high-risk runs; only a direct controller `run_begin` that omits the policy preserves the legacy contract.

`repair-worker` is available only in a newly approved repair plan after the prior author has settled and its defect transfer has named the findings, paths and checks. It does not retry or take over an interrupted implementation, weaken graph/lease fences, or replace parent acceptance.

The runner uses the existing controller for dependency maturity, leases, scope conflicts, candidate ownership, merge queue, and gates. It creates isolated worktrees and real root sessions for ordinary execution. The test-only `--mock-executor` is lab-only and visibly recorded; it exercises real Git and controller transitions without provider calls. The runner has no comparison or fault-injection command. A later, separate bounded comparison may use immutable attempts and receipt ledgers to compare one serial and one parallel run; it must retain every failure and make no general performance claim.
