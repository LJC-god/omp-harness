# Verification and delivery

Read before implementation or review; apply only checks relevant to the assigned behavior. Sol writes and maintains planning, task and decision files, including their project-documentation paths. Each implementation artifact, including implementation documentation, has an assigned author; Sol owns scope, coordination, read-only inspection/checks and final acceptance against the original labelled requirements. A worker PASS, saved checkpoint, successful build or gate receipt cannot cover a missing user outcome. Configuration experiments use ~/.omp/agent/notes/omp-evaluation.md and remain separate from everyday acceptance.

## One assignment, one verifiable result

Use six compact fields in the existing assignment, without a new document or schema:

1. Goal: one observable outcome, with the original requirement labels AND their exact relevant text; never require a child to infer the numbering.
2. Decisions: accepted behavior, dependencies, existing interfaces and material exclusions.
3. Ownership: actual absolute cwd, allowed paths, source/baseline and Git owner.
4. Checks: exact focused behavior command, necessary package type check, and absolute D: evidence destination outside source. Inspect scripts once so focused arguments really select focused tests.
5. Stop: the observable completion condition and implementation/check/handoff budget. Under a 30-minute cap aim for 10-15 minutes implementation, 5-10 minutes checking/repair and handoff near minute 25; scale for another cap. These are planning targets, not a new cancellation timer. Stop expansion at the check boundary, not halfway through a data-safety invariant.
6. Handoff: changed paths, actual source, executed commands/results, retained evidence, task-owned processes, blockers and the smallest unchecked remainder.

## Decompose before dispatch

For a complete product, apply product-planning.md and workflow-baseline-v1-20260921.md first: targeted research, task table, frozen semantic scope/interfaces/invariants/task graph and an explicit parallel/serial decision. Purple PLAN independently reviews those frozen inputs before dependent implementation without waiting for diagram rendering. Start from an observable original requirement outcome, then divide it into single-author business-capability work packages; the initial author's reading, editing, focused checking, development-time visual-feedback corrections, and routine self-repair stay inside that package. Confirmed final-review defects transfer as repair-worker root-cause packages after the prior writer settles. Keep strongly coupled behavior, a shared invariant, compatible small edits, or a compatibility change with its caller under one owner. Do not split merely by file, model, or a fixed number of minutes.

In Decisions, name each dependency's required input and its needed maturity: an agreed contract, an available commit, or an integrated result. Separately name conflicts: overlapping paths and shared behavior/invariants can require serialization even without a dependency. Resolve a critical unknown with a bounded investigation that returns a concrete decision or evidence. When an interface or integration is uncertain, first deliver the narrow end-to-end path needed to test that assumption, while retaining the full accepted scope. For an applicable broad compatibility migration, use expand, migrate in independently checkable batches, then contract; do not force this shape on ordinary features.

The six fields must let a new author start without prior chat: Goal names the parent outcome and whether the purpose is discovery/recommendation, plan persistence or implementation; Decisions states the frozen inputs/outputs, maturity and conflicts; Ownership gives the exact boundary; Checks proves the package behavior; Stop gives its local acceptance; Handoff gives the next owner usable output. Define the parent's integration acceptance at the same time as author checks. Record request, plan-ready, first-effective-author, foundation-ready, dispatch, blocked, handoff and final timestamps in the existing task table/evidence; the 15–20 minute first-effective-author target is diagnostic only and never waives a required gate. A union of local PASS results does not itself prove the original user journey. Root checks the payload against its frozen source before dispatch and checks returned decisions before acceptance; missing consequential decisions are `SOL_DECISION_REQUIRED` with evidence/options, while local algorithm, focused-test and compatibility investigation remains allowed.

Keep full product scope in the parent plan. Group compatible small edits with the same owner; do not create a worker per file. Do not bundle several independent journeys into one capped invocation. Initial authors run scoped checks and repair their own failures, missing imports and touched-file formatting within their ownership. A confirmed post-implementation defect transfers as one bounded root-cause batch to repair-worker after the original writer has settled; do not return it to the original author by default. Reject blanket bans on all tests/type/browser checks; mechanical edits need only an appropriate diff/import check. Sol performs broader integration assessment and reuses evidence valid for unchanged source; integration code remains with its assigned author. A build containing the same type check does not need a duplicate parallel type check. No project-wide formatters or suites merely for a tiny fix.

If time/capability is insufficient, preserve a safe partial result and name missing checks. Do not begin a known long operation near the cap without assigning its continuation. Quiet model/tool work alone is not a deadlock. After interruption inspect execution and side effects before continuing only the unfinished portion; detailed recovery is in ~/.omp/agent/notes/session-handoff.md and coding-procedure.md for controlled work.

## Review closure

For a newly declared complete product, set `workflow: "product"` and explicitly set `userFacing` once from the accepted scope. The runtime, not Sol's tool arguments or prose, records the reviewer role, task identity, current cwd/branch window and source identity. Native v4 reviewer output requires top-level `status`, nonblank string `summary`, nonempty string-array `evidence` with at least one nonblank item, and string-array `findings`; `status` is exactly `PASS`, `FAIL`, `BLOCKED`, or `INCONCLUSIVE`. Before every v4 mandatory review, Sol uses root-only `omp_checkpoint` `assign_review` with the reviewer, `purpose: "final"`, `dispatchKind: "native"` and an exact ordinary TaskTool `name`, or `dispatchKind: "controlled"` and its exact `idempotencyKey`; the runtime consumes that one assignment only on the matching dispatch at the recorded cwd/window/source. Missing, stale or mismatched assignment is development evidence, never final evidence. Controlled frozen contracts and v2/v3 checkpoints retain their existing receipt contract. A final product needs independent red security-reviewer, blue verifier, and purple-reviewer PASS evidence; `userFacing: true` also needs the applicable `gpt-visual-director` and native `experience-reviewer` PASS evidence. Each v4 final receipt must settle after an observed implementation task and have identical dispatch, settlement and current source fingerprints. A later running, invalid, failing, blocked or inconclusive final same-role check supersedes an earlier final PASS until its proper recheck; development receipts remain retained separately.

Track findings in existing textual evidence by original report/ID, severity, trigger and source: ADOPTED stays open until a repair and executed relevant check exist; REJECTED needs inspected evidence that it does not apply under agreed behavior; MERGED names the surviving finding without dropping an independent trigger. Record non-blocking residual work in the existing backlog. Distinguish introduced, exposed and independent pre-existing defects. Cost or a worker assertion cannot reject a valid blocker.

Follow-ups cover findings, repair diff and affected callers, reusing unchanged coverage. Required independent gates, confirmed P0/P1/data-loss blockers and arbitration remain authoritative. Never add disposition fields to strict task/finding schemas or relabel historical PASS receipts as current. After two failed repair rounds on the same boundary, Sol traces the shared lifecycle/callers and revises the repair plan; this is diagnosis, not an approval gate or permission to waive defects.

## Mandatory product red, blue and purple acceptance

Every new complete product uses workflow: product with explicit userFacing at task start, regardless of native or controlled execution. Small maintenance work retains its relevant risk/behavior checks; do not label a complete product standard to bypass acceptance. Runtime v4 completion requires current root-assigned `purpose: "final"` independent security-reviewer (red), verifier (blue) and purple-reviewer PASS receipts, plus applicable gpt-visual-director and experience-reviewer final receipts for user-facing products. Saved v2/v3 checkpoints and frozen controller contracts retain their earlier requirements; v4 recovery rejects unknown versions or a missing captured purpose instead of silently rewriting or reusing an older checkpoint.

Purple PLAN reviews frozen requirements, decomposition, interfaces, invariants, owners, task graph and real branches/parallelism before dependent implementation. It does not wait for rendered diagrams. For a multi-module product, an assigned existing author creates required Archify JSON/rendered HTML alongside approved implementation; simple work may retain its existing compact representation. Validate required views before final freeze. After foundation verification, reassess the remaining parallel opportunities. This planning review cannot count as final delivery acceptance. Artifact writing belongs to its assigned author; purple remains read-only.

After integration, settle writers and conflicting leases, capture one final candidate, and collect the complete planned reviewer coverage before ordinary repair. Dispatch independent red security/risk and blue technical/behavior reviews; they may run concurrently with separate isolated test data/resources. User-facing products also require the applicable single visual review and real-user journey review. Do not cancel an accepted final role because another review fails: only active security/data damage or a coverage-blocking prerequisite stops collection, and the blocked remainder is recorded. Give each reviewer original requirements, source identity, affected scope, documented startup/destination and evidence references. Omitted native outputSchema receives the runtime's canonical strict top-level status, nonblank string summary, nonempty string-array evidence with at least one nonblank item, and string-array findings; an explicit schema must require equivalent field types and recognized status. Process exit 0 or prose PASS alone does not count. Show actual role, resolved provider/model and thinking level for every dispatch; do not silently substitute a different model for purple.

Once those reviews settle, dispatch purple DELIVERY in a separate native task to reconcile requirements, current receipts, actual artifacts/commits, required diagrams and their evidence, launch instructions and exact delivery destination. Purple inspects evidence instead of repeating all tests, and performs this reconciliation even when another final role has already returned FAIL where its inputs remain available. Missing evidence is BLOCKED/INCONCLUSIVE; concrete defects are FAIL. Sol assesses the combined evidence and marks the product checkpoint complete only when all required current-source receipts pass. The runtime binds receipts to the current task window, dispatch and settlement source, successful implementation provenance and latest reviewer attempt. A valid canonical top-level `status: "PASS"` output is structured, but does not set `deliveryReady`: when it is false, the runtime persists an `INCONCLUSIVE` receipt rather than treating the output as malformed. Final-ready dispatch is allowed only after the candidate's current-source prerequisites have settled. Earlier failure collection remains allowed; preserve all failures and reuse only valid current-source incremental receipts. A PLAN PASS, stale result, failed task, `deliveryReady: false`, or pending recheck cannot close delivery.

Sol consolidates and deduplicates the collected findings, traces shared causes, and transfers one root-cause batch to repair-worker after the original owners settle. Truly independent repair packages may run in parallel within the established ownership and four-author limits. A repair receipt records resolved findings in evidence; `findings` retains only unresolved issues. Reuse a settled PASS only when scope and source fingerprint are unchanged. A changed fingerprint requires every mandatory role to produce a new current-source incremental receipt for affected scope and attest unchanged coverage, without mechanically rerunning unchanged tests. Never treat an older-source PASS as the new receipt or launch a new full review for each finding. Saved Runtime v3 checkpoints still require every mandatory receipt to be PASS on the current source. Reviewer arbitration is only for a material disagreement supported by evidence, not a mandatory fourth round. Existing mandatory controller arbitration still applies once triggered; purple and Sol cannot waive valid blockers. A controller run/merge succeeding is not parent product completion.

## Persistence and integration

Before changing persistence, migration or async ownership, trace owner identity, read/write entry points, context captured before await, switch/delete invalidation, durable commit, rollback/retry and synchronization. Keep coupled invariants under one owner with representative race/write-failure checks. Inspect startup/callers as well as parsers: absent, malformed, unsupported-version and unavailable storage are distinct; seed only absent data. Verify failed writes/removes leave original data recoverable. Never test migrations or cleanup on real user data.

For a complete integrated product establish the actual database/driver versions, migration command and core role-specific journeys early. Start a clean-install check from the README in a fresh isolated environment and distinguish first administrator creation from idempotent rerun behavior. Distinguish static Docker inspection from live container startup, and multiple isolated accounts from a cross-device shared-data journey. Missing Docker/psql alone does not prove no route exists; reuse a verified local recipe (when relevant, D:/OMPData/registry/outcome-fixes-20260914/README.md). Mocks/PGlite do not prove PostgreSQL multi-connection concurrency. Booking/inventory coverage includes duplicate requests, contention, ownership and cancel/rebook where relevant. Name missing environments and journeys precisely; an unavailable required route cannot PASS.

## UI and behavior evidence

### User-experience acceptance

For complete user-facing products and substantial user-journey changes, Sol dispatches experience-reviewer as a separate ordinary native task and context. verifier keeps technical verification/reproduction; security and visual roles keep their scope. No extra controller gate or user approval is added. Routine copy/style edits need only their affected checks. For controlled projects, settle implementation tasks and conflicting leases before the native UX task; retain every required current-source technical/security gate and record UX evidence in the existing parent requirement checklist. Do not send this role to project_spawn, downgrade a run, replace a gate receipt or bypass an ownership conflict. Repairs follow the existing controlled route and invalidate affected evidence. Frozen running contracts stay unchanged; older receipts do not cover newly assigned journeys.

Start from the user's accepted requirements and documented launch/install entry, not the author's claimed PASS or private testing shortcut. Exercise representative journeys for each materially different role with isolated test accounts/data: first use and discoverability, completing the core goal, understandable success/error/loading/empty states, relevant invalid-input recovery, and restart/persistence where promised. Use real mouse/keyboard/touch inputs as relevant, including a narrow view for responsive products. Verify a cross-device shared-data journey when requested; several names in one local ledger or isolated accounts are not evidence of collaboration. Reuse valid unchanged technical evidence and gpt-visual-director's visual coverage rather than repeating them; a screenshot cannot prove an interaction.

Record each assigned journey's requirement, starting state, actual actions, observed outcome, source identity and evidence in the existing verification evidence. Distinguish product defects from unavailable environment/driver and subjective polish. Missing user-launch instructions, an unusable agreed install destination, or an unexecuted core journey cannot become complete-product PASS. Return concrete findings to Sol; repair-worker repairs confirmed defects after the implementation owner settles, and the same experience reviewer rechecks affected journeys. Sol closes every original requirement and reports actual coverage; no new dashboard or separate handoff document is required.

### Evidence boundaries

Use ~/.omp/agent/notes/frontend-workflow.md for UI authorship and the single visual review; browser execution uses ~/.omp/agent/notes/browser-verification.md. Read actual tool contracts after an API error rather than guessing variants. Real mouse/touch/keyboard acceptance needs that input and its postcondition; synthetic events, direct state/DB/handler calls and screenshots establish narrower facts. Preserve failed real-action results until corrected or reported; do not hide them behind weaker tests. Distinguish product FAIL from BLOCKED/INCONCLUSIVE coverage.

Desktop background promises require close/hide, tray restoration and explicit exit. A live PID proves only survival. Image-copy promises require real copy and paste into the agreed target (or a labelled local rich-text target when none was specified); preview/inlining tests do not prove clipboard delivery. Re-run a failed inspection successfully or report its gap.

Keep final artifacts outside source from the start. Include source identity, command/URL, actual mode/viewport and observed postconditions. Before cleanup, verify retained references exist; delete only named task-owned temporary files, never the sole acceptance evidence. Full desktop builds belong at the final candidate or an earlier concrete native/packaging risk, not every Web repair.

## User startup and delivery destination

Keep one launch recipe in the existing README/help: exact root/executable, prerequisites, initialization/migrations, actual commands/URL, data location and restart. Reuse scripts; add a small root launcher only if entry points are fragmented. Do not invent infrastructure for a static/desktop product or put secrets in documentation.

Execute the user's documented launch from the intended root/install directory, perform a representative core action and restart/persistence check when relevant. Use isolated test data and task-owned available ports; never kill another project's server. Hidden agent-only harnesses or Responding=True do not prove the full journey. Report unavailable infrastructure and uncovered behavior rather than complete-product PASS.

An explicit installation/output directory is an acceptance requirement. Registry entries, previous defaults and installer discovery describe current state, not authority to replace the user's target. Compare the selected build or verified package payload with the artifact at that exact destination using hash/version/provenance, then launch that copy. Check relevant shortcut targets; preserve user data and do not silently delete another installation. If the destination cannot be honored, report the concrete conflict. Report installed, smoke-tested and left-running as separate facts; a supervised smoke process is not guaranteed to remain running after its owner exits.

Before completion reconcile every original requirement, actual delivery path and current-source evidence. Visual failures need the same reviewer's affected-view recheck or an explicit remaining gap. Mark superseded results historical in the existing summary; do not delete failures or leave contradictory final claims. Return results, relevant checks, source/commits and limitations without a new dashboard or approval chain.
