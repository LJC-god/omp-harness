# Skill selection

Read only when selecting a method for new-product planning, complex engineering or visual design. Model ownership is defined in main-agent-orchestrator; skill framework examples do not override it.

## Skill contracts and technical choices

### PM and Matt routing

- For a product created from scratch, Sol authors the planning decision/checkpoint: target user/problem, first useful journey, user-selected delivery depth, complete scope, stack, architecture, invariants, interfaces, decomposition, acceptance and consequential unknowns. A clear sufficient brief needs no interview or workshop; it still follows product-planning.md for bounded research, task boundaries, module/task diagrams and a parallelism decision. For a one-sentence new complete-product brief, delegate one bounded pm-worker full product definition by default, covering scenarios, evidence versus assumptions, positioning and innovation recommendations with value/tradeoffs, full journeys, roles/data/rules/invariants, states/errors/cancellation/recovery, UX direction, scope/priorities, acceptance and unknowns. PM uses the A route in `skill://pm`'s `references/method-a.md`: Dean Peters discovery → JTBD → voice-of-customer → opportunity-solution-tree → user-story. Give PM the original brief, existing evidence and challengeable assumptions instead of a pre-frozen feature list; PM owns bounded exploratory research using the discovery reference and shared tools; follow product-planning.md for exceptions and limits. Sol accepts scope and maps selected innovations to implementation and acceptance; PM returns source-linked findings with native session/receipt identity; inaccessible evidence or consequential `WEB_RESEARCH_REQUIRED` gaps go to Sol without replacing its decisions. PM writes the authorized PRD/research authority files, while Sol's decisions file records adjudications; engineering documents reference stable PRD IDs rather than reproducing product rules.
- For complex engineering (an unresolved module/data-flow design, a multi-stage feature, substantial refactoring, or a hard-to-reproduce bug), assign the relevant author to use `skill://matt` and select one capability for the current phase. Matt is a method library, not a new agent/controller. Do not run its entire workflow chain. Sol keeps coordination; module ownership and visible UI review follow main-agent-orchestrator.
- Explicit file deletion, routine Git operations, documentation edits and small understood fixes skip PM/Matt unless the user explicitly requests them. A new folder or Git repository alone is not product discovery. A substantial new feature can use PM for an actual scope question without making every engineering change a product workshop.
- Keep the brief/selected capability and evidence in the existing task/checkpoint when useful; do not add a separate handoff contract, approval hash, mandatory ticket system or review gate. Existing authorization carries forward. Load only the current phase, not every PM/Matt reference. Required skills in existing frozen controlled contracts remain required.

Controlled worker contracts specify applicable required skills and their references; optional/forbidden skill fields are needed only when relevant. Assigned native work follows applicable skills without a separate contract or manifest ceremony. Read required skills before work; optional ones only when triggered; never load forbidden ones. Default one primary plus zero to two supporting skills. Match name/hash to the manifest: missing is SKILL_UNAVAILABLE, mismatch is SKILL_VERSION_MISMATCH, conflicting scope is TASK_CONTRACT_BLOCKER. Do not simulate reading. A selected method never authorizes Sol to implement artifacts.

UI authorship, independent client-logic ownership and visual review follow main-agent-orchestrator and frontend-workflow.md; do not infer ownership from a frontend directory or upstream example.

fixed-route selects a maintained architecture profile for projects created from scratch; read its compact skill and architecture-catalog.md before scaffolding. Sol chooses the profile and domain depth from actual requirements and verifies only unproven adaptations. Existing projects retain their working stack; a recipe-only entry must not be described as a verified scaffold. Choose a suitable UI scheme within the selected framework. Frontend ownership and the single visual review follow main-agent-orchestrator; baoyu-design is optional when relevant.

For a new React/Vite admin or workbench selected by fixed-route, apply the catalog's Tailwind + shadcn/Radix + Lucide baseline through `skill://shadcn` after the product direction is frozen. The skill is the component/registry method, not a design review or a reason to replace an existing stack. In OMP, upstream Claude-specific `allowed-tools` and `!` command directives neither execute nor grant tools: use only actually available read/bash tools, explicitly run the selected project's `shadcn info --json` command in its real cwd, and inspect its returned context. `mcp.md` documents an optional method and does not prove an MCP server is installed; do not install one solely for the skill. The current Business C recipe does not yet include this baseline, so its verified status does not claim that it does.

`skill://baoyu-design` is the complete upstream design package. For high-fidelity design artifacts or interactive prototypes, baoyu-design-worker may use it; for product-source work, frontend-worker may use the skill directly. New-project depth/location intake precedes design-skill loading; Sol does not preload Baoyu's full references or variants just to ask the user where/how far to build. OMP is the harness regardless of model provider: native ask and the local browser recipe take precedence over Codex-only or .question.html examples. Choose one primary design method for the deliverable; do not force every frontend task through a separate prototype, board or all built-in skills. Reuse the user's known scope, fidelity, design context and destination instead of repeating upstream questions. Routine unspecified artifact output may use `designs/<task>/` inside the verified project. Keep upstream skill files intact; OMP's model roles, fixed technology route, ownership, authorization, research routing, Ponytail frontend exclusion and single visual review govern integration. Missing optional export or asset services do not justify inventing success or demanding new accounts for unrelated work.

### Architecture and workflow diagrams

For complete products, follow product-planning.md: use `skill://archify` for the required JSON source and rendered interactive HTML that record module/data flow and task dependencies. Sol owns factual scope and semantics; one assigned author mechanically renders, validates and retains the artifact. For ordinary small maintenance, use Archify only when a diagram improves understanding or is explicitly requested; prose may suffice. Do not add a model, a screenshot gate or agent stages merely to draw it. sonic may own the bounded artifact or source-fact extraction; there is no default deepseek-worker stage. Preserve source references/version and apply existing review rules without another approval gate. A diagram explains the implementation; it is not runtime evidence. Keep upstream skill files intact and load only the matching schema/example and necessary references.

### Frontend skill selection

For new visual work or a substantial redesign, select one primary design method in the existing assignment. A small behavior fix does not require restarting visual discovery.

| Deliverable or current problem | Skill |
| --- | --- |
| Product screens, high-fidelity design artifacts, interactive prototypes | `skill://baoyu-design` |
| Brand sites, landing pages, distinct visual composition | `skill://frontend-design` |
| Interaction polish, component feedback, motion design | `skill://emil-design-eng` as a task-relevant supplement |
| Accessible names, keyboard/focus behavior, form accessibility | `skill://fixing-accessibility` for the affected surface |
| Jank, animation rendering cost, scroll/measurement problems | `skill://fixing-motion-performance` for the observed problem |
| Pre-design navigation, journeys, component/state inventory, responsive direction | `skill://ui-ux-design-audit` design pass when the scope needs it |

Pass a concrete goal when invoking a skill, especially Emil; an assigned implementation is not a bare readiness request. Read only the selected entries/references when first relevant and do not reload unchanged text every turn. Do not run all skills, add specialist agents or create a new review gate just because they are installed. Existing model/stack choices and frontend quality goals prevail over upstream framework examples or aesthetic heuristics. Translate examples to the current stack; do not migrate Vue to React to use a skill. Preserve intentional design and interaction quality while fixing measured performance or accessibility problems. The visual-review role reviews the chosen direction and current rendered evidence; motion/keyboard claims need actual interaction evidence, not a static screenshot alone. Ponytail remains excluded from frontend work.

`ui-ux-design-audit` has two separate uses. Before implementation, its design pass can give Sol and the frontend authors a concrete navigation, journey, state and responsive-direction brief. After implementation, its audit checklist can inform an independent review, but it does not grant final acceptance and must not be the author’s self-signoff. The existing `gpt-visual-director` and `experience-reviewer` remain the independent final visual and journey reviewers.

Sol resolves a catalog mismatch with a recorded requirement and bounded feasibility evidence under existing engineering authorization. Ask only when an explicit user constraint must change, a required model needs substitution, new external authorization is needed, or an actual resource/data conflict cannot be resolved safely. Existing authorization carries forward. Do not create STACK_OVERRIDE/Strategic Controller paperwork. Ordinary profile selection, component and styling choices need no repeated approval; preserve an existing project's stack and never silently replace an explicit user constraint.
