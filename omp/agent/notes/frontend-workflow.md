## Design and skills

New visual work needs a direction suited to its subject/audience, a memorable feature, polished hierarchy and complete interaction states. Quiet and expressive designs are both valid. Existing-product repairs preserve its visual vocabulary and assigned scope. Do not cut design ambition, typography, assets or purposeful motion to minimize code. Ponytail does not apply to UI design, implementation or review.

Select one primary design method from ~/.omp/agent/notes/skill-routing.md, with zero to two relevant supplements. Keep existing stack/components and adapt upstream examples; no React migration to use a skill, compulsory prototype, concept board or proprietary UI library. Reuse accepted scope/location before loading design references. Optional asset/export services do not justify invented success or unrelated account requests.

For a substantial new journey, `skill://ui-ux-design-audit` may be the pre-design method: produce a concrete navigation, key-flow, information hierarchy, component/state and responsive brief for the frozen plan. It is development input, not a reviewer receipt. Final visible/UI-journey acceptance remains independent through the assigned visual and experience reviewers; do not let the implementation author use an audit checklist as final signoff.

## Affected-state acceptance

Implement and exercise the affected controls/states: focus, selected/checked, expanded, invalid, disabled/loading, hover or motion where relevant. For dialogs cover focus entry, Tab containment, Escape, return to trigger or a safe fallback after deletion, and scroll restoration. Preserve keyboard use, accessible names, contrast and forced-colors support. For responsive changes use relevant narrow and wide viewports, not a universal 390px gate.

Within scope remove unintended scaffold assets/default styling; preserve intentional brand colors and suitable native controls. Unexpected colors require computed-style/cascade/font/asset inspection, not grep alone. Do not use blanket appearance/outline removal or escalating !important to hide a cause. Explain relevant native-control limitations; a new component library is not mandatory.

Read ~/.omp/agent/notes/browser-verification.md for the working driver. One named runtime owner operates the shared production preview and exclusively restarts or rebuilds it; that owner keeps the identified preview, source/build version and runtime alive until all assigned consumers settle. Reviewers use separate accounts/data and do not disturb it. Keep all evidence artifacts outside source from the first call. Final visual evidence comes from current production preview where supported, after fonts/layout/transitions settle under bounded conditions; a build completed later does not turn dev screenshots into production evidence. Record actual source, mode, URL and viewport outside source. Real actions prove interaction; screenshots prove only visible states. Login screenshots cannot cover unseen authenticated screens.

## Single visual review

For a nonvisual frontend author, obtain scoped development-time feedback from a role with actual visual capability after shared UI foundation formation and whenever the assigned complexity or observation warrants it; return it to the original assigned author within its current scope, never as final acceptance. For final user-facing acceptance, Sol first arms a v4 root-only `omp_checkpoint assign_review` assignment for `gpt-visual-director` with `purpose: "final"`, `dispatchKind: "native"` and the exact ordinary TaskTool `name`, then dispatches that named task once with current screenshots, intended direction and affected states. Development-time visual feedback has `purpose: "development"` or no assignment and remains useful feedback only; a reviewer PASS, task prose or output cannot upgrade it. Do not add aesthetic-reviewer and visual-reviewer for the same scope. Pure logic needs behavior checks instead. Review visible hierarchy, readability, clipping, operation clarity, design completeness and applicable accessibility; taste alone does not block.

For complete user-facing products or substantial user journeys, the separate native experience-reviewer owns required independent user-experience acceptance under ~/.omp/agent/notes/verification-evidence.md. The visual director reviews appearance and visible clarity; the experience reviewer exercises the documented user entry and actual workflows; verifier retains technical gates. Reuse their respective evidence without repeating full suites or visual reviews. A visual PASS alone never closes an untested user journey.

Return PASS | FAIL | BLOCKED | INCONCLUSIVE with concrete evidence, blocking defects and optional polish separated. Missing/offscreen/stale evidence and suspected transition frames need coverage or a settled capture, not an invented product FAIL/PASS or inferred CSS diagnosis. Static images cannot certify motion, keyboard behavior or performance. Confirmed final-review UI defects go through Sol as a repair batch for repair-worker after prior writers settle. Reuse the same reviewer for affected views after repair; unchanged coverage follows verification-evidence.md's current-source attestation rule. Sol closes original acceptance using the broader verification note.
