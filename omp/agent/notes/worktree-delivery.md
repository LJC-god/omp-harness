# One-task worktree delivery

Use this method only for one bounded task whose original requirement, author, target branch and single Git integration owner are already settled. It connects existing OMP controls; this serial procedure itself does not add a scheduler, task graph, claim protocol, merge queue, cross-root lock, database record or recovery mechanism. This remains the serial step 2 procedure. `task-graph.md` is an opt-in step 3 supplement for declared independent task worktrees, and `merge-queue.md` is an opt-in phase after graph delivery; neither replaces the preparation, recovery, or Git-owner rules below.

## Prepare the two real roots

Sol begins in the actual target worktree/root. Before creating the prospective worktree, run the existing read-only workspace preflight against its intended path/nearest existing parent, then inspect the target repository status, target ref and HEAD, the common Git directory, existing OMP project/workspace status, unsettled tasks and writers. Stop on a dirty target, another writer, an uncertain task, unresolved ownership or any target/worktree identity discrepancy. Do not use a worktree to evade an existing occupancy conflict.

From that clean target state, create one direct child of `D:/OMPData/worktrees` with a dedicated task branch based on the recorded target SHA. Record the target root/ref/SHA, task worktree path, branch and base SHA in the existing checkpoint or handoff. A linked worktree has its own `.git` location and the controller already pins its root, Git directory and common directory after registration; this is identity protection, not a cross-worktree integration lock.

For the resolved values, the Git owner may use the standard Git operation `git -C <target-root> worktree add -b <task-branch> D:/OMPData/worktrees/<task-id> <target-sha>`. Substitute only inspected, recorded absolute paths and SHAs; do not use a guessed branch name or an unverified current `HEAD`.

For a new `integration-v1` run, freeze a controller-approved direct D: diagnostic root outside both source roots before `run_begin`. `run_check` drains and hashes the full raw stream, redacts recognized quoted JSON `token`, `access_token`, `id_token`, and `authorization` values plus Bearer values before retaining a bounded sanitized head/tail JSON, and binds its actual path and hash to completion. The redactor carries recognized state across pipe chunks and retained cuts, so no fixed tail skip is used. Raw `bytes`/`sha256` and `rawGap*` remain distinct from sanitized retention fields (`sanitizedBytes`, `sanitizedRetainedBytes`, `gap`, and `gapBytes`). Storage never stops the command. The sanitizer is not a universal secret detector and the artifact can omit sanitized middle or partial diagnostics. An absent failed write has no actual `path` and records its authorized `attemptedPath` with `missing: true`; a partial regular file has its actual path/hash but remains `write_failed`. A missing, tampered, write-failed, stream-failed, cancelled, or timed-out diagnostic cannot complete the check even when the process exit is separately recorded. Historical runs that froze no diagnostic policy remain historical; do not resume a new-policy run on an older controller or relabel it as legacy.

Native `task` has no per-call cwd. Before either `/move`, settle active controlled tasks and release the related leases/occupancy under the existing rules; a returned author result alone does not authorize moving past an uncertain task. `/move` is a native slash command accepted only by the session front end after streaming has ended, not a shell command or model tool; continue dispatch only after it succeeds and the new cwd is verified. In that real worktree context, rerun the existing preflight and `workspace_prepare`, register or reuse the worktree project, call `run_begin`, `baseline_capture` and `generation_get`, acquire the appropriate existing lease, and call `project_spawn`. A new eligible standard integration run may declare `executionPolicy: "integration-v1"` with frozen `checkCommand`; its root-observed `run_check` supplies `integration_check`. High-risk, omitted-policy, and already-frozen runs retain their existing required gates. Never pass a fake host cwd or rely on an assignment sentence to redirect the author. Use clean, pinned-base `git worktree add` here; this method does not use or extend native `/wt`. Keep the existing risk classification; an isolated test's mechanical risk does not classify production work.

## Author, candidate and verification

The author changes only the task worktree and runs the assigned focused checks. The Git owner commits the exact verified, task-owned paths and records the resulting author HEAD; an author commits only when Sol explicitly delegated exclusive Git ownership for this task. Before moving on, the Git owner confirms the task worktree is clean. A successful author receipt is not a merge receipt.

Sol then captures the current target SHA again. The task branch already contains the recorded author HEAD. In that task worktree, the single Git owner merges the current target SHA into the task branch, for example with `git merge --no-edit --no-ff <current-target-sha>`; the resulting task-branch HEAD is the candidate. A confirmed post-implementation conflict or defect transfers to repair-worker only after the original author settles; an incomplete author attempt remains with that author until settlement. Record the candidate SHA and prove with Git ancestry checks that it contains both the recorded target SHA and author head. Verify the actual candidate, not the earlier author state. Every source change invalidates earlier current-source evidence. For `integration-v1`, the root runs its frozen `checkCommand` through `run_check` against that candidate; otherwise run the frozen required gates in the candidate's real worktree context. Keep author focused checks and parent integration acceptance distinct.

`sourceFingerprint` compares the source state; it does not make a receipt portable across roots. A controlled receipt is bound to its project, run, generation and owner, and the controller verifies it in that project/run context. Therefore even if two worktrees yield the same fingerprint, a PASS recorded for the task worktree cannot be copied as a controlled gate PASS for a different target-root project. If the target has its own controlled run, obtain that run's frozen required gates against its own current source as usual. A successful candidate validates only the stated candidate checks; it does not automatically complete a product checkpoint.

## Serial integration

The Git owner returns to the actual target root with `/move`, verifies root/project ownership again, and checks: both task and target worktrees are clean; target ref and HEAD still equal the recorded candidate base; Git/common-directory identities still match; and the candidate still contains that target base and author head. Only then may that one owner run `git merge --ff-only <exact-candidate-sha>` from the target root. Record the resulting target HEAD as `mergedHead` and preserve the commit/check evidence in the existing checkpoint and handoff.

If the target moved, a check failed, ancestry differs, or `--ff-only` fails, stop. Do not force-push, reset, overwrite the target, or claim an automatic retry. Rebuild and revalidate a candidate only after Sol has resolved the changed ownership/state under the existing rules. This serial procedure runs one task and one integration at a time; a graph-delivered node may instead use the distinct FIFO/common-directory lock protocol in `merge-queue.md`.

## Interruption and recovery

For an interrupted author task, follow the existing receipt inspection and `task_reconcile` route. Preserve the branch, worktree, retained session and evidence; do not reuse an uncertain task key or silently create a replacement branch. For a lost merge response, first inspect the actual target HEAD, ancestry, target ref and refs before taking any further action. Any state that cannot be explained by those facts is blocked: leave the branch/tree/evidence in place, inspect task-owned processes without killing unknown processes, and escalate the concrete ownership/state conflict. Do not treat elapsed time, an absent response or a controller PID as proof of a safe retry.

## Required handoff facts

Use the existing checkpoint and handoff text to retain: task/run identifiers; task worktree and branch; target root/ref; base SHA; author HEAD; current target SHA; candidate SHA; executed candidate checks and evidence; resulting merged HEAD; and any remaining controlled gates or product requirements. These facts make the next real session able to inspect the work without inventing a cross-root state machine.

## Step 3 (opt-in): declared dependency graph

After the serial preparation above, Sol may use `notes/task-graph.md` for multiple independent, real task worktrees sharing the same Git common directory. Each participating root still runs the existing preparation in its actual worktree, then atomically claims its declared node before `project_spawn`. A graph claim does not create/move/clean a worktree or transfer Git ownership. It protects only declared path/resource conflicts and dependency maturity. After a node is delivered, use either this document's serial candidate/target-root procedure or the separate explicit queue protocol in `merge-queue.md`; do not mix their state or infer a queue attempt from a graph claim.

## Limits and next phase

This is a serial, manual Git-owner procedure. The optional task graph can atomically claim declared dependency-ready nodes and reject active declared scope/resource conflicts. The separate queue can serialize one later integration attempt, but neither method detects semantic conflicts across independent worktrees, creates/moves/cleans worktrees, automatically retries, or turns an unexplained merge into a safe retry. Those limits must not be inferred away from either method.
