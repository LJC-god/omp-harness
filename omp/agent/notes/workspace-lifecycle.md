# Workspace preparation and new-project intake

Read for new-project intake, destination selection or a workspace ownership conflict. Routine established-project changes skip this note; their product/software artifacts still belong to the assigned author under main-agent-orchestrator.

## New-project intake and delivery depth

Before scaffolding, inspect the intended root and applicable rules. Use the standing user preference below instead of an automatic depth/location questionnaire. Do not preload PM/design libraries merely to ask intake questions. The implementation owner loads the chosen design method after scope/root are known; use one strong direction unless the brief actually needs a consequential design choice. OMP is the harness even with an OpenAI model provider; use native ask for a real missing choice.

Standing preference (2026-09-18): a request to complete a system/product with listed features authorizes complete implementation and local usable delivery of that scope, including the necessary UI, persistence/API/auth, integration, checks and launch instructions. Work in the explicitly named root, or the current independent project folder where the user launched OMP; do not add a child folder or ask the user to choose prototype/MVP/full again. Respect explicit prototype, static-only or deployment requests; a complete static site needs no irrelevant backend. Public deployment, paid services or missing third-party credentials still require their actual authorization/input. For a new fixed-route project verify concrete dependency versions/commands before dependent writers begin, retaining the recipe in the existing brief/README.

Reuse supplied requirements and retained choices. Ask only for a consequential unresolved product decision, an ambiguous/occupied destination or an actual external blocker; bundle related missing choices once and continue independent work. A container folder, unrelated existing application or registered ancestor is not permission to overwrite, nest or relocate a project. If the user explicitly requests a new child folder, choose a sensible name after collision checks. An unanswered necessary question remains pending; elapsed time is not authorization.

Once resolved, distinguish user-confirmed intent from the implementation plan in the existing brief/checkpoint. Keep delivery depth, exact project AND installation/output destinations, agreed workflows, exclusions and model/stack constraints traceable to the user's messages; inferred design choices are proposals, not user authorization. Revise milestones and methods as evidence changes without silently weakening the confirmed scope. A user correction updates the relevant requirement, not unrelated accepted decisions. Complete the whole agreed delivery through verified milestones. Use the existing project specification if present; do not introduce a parallel spec tree, approval step or mandatory PRD. Preserve the existing Git/root ownership rules.

Before workspace_prepare, Git initialization or writer dispatch, run the read-only helper `python ~/.omp/agent/lib/workspace-preflight.py --root <absolute-project-root>` with shell cwd at that exact existing project root (or its nearest existing intended directory for a prospective folder). It reports registered ancestors/descendants, shared ancestor Git roots, workspace writers, unsettled tasks and live leases; it neither registers nor unlocks anything. A historical registered ancestor is REGISTRATION_OVERLAP even with no active session; a shared Git root is SHARED_GIT_ROOT; possible live work is OCCUPANCY_REQUIRES_INSPECTION. NOT_FOUND from project_get, no writers from workspace_status, and successful workspace_prepare do not prove independent registration is possible. A missing/unreadable control database or failed inspection is UNKNOWN, not clearance. For any possible occupancy, use native workspace_status/project_get and existing ownership rules to distinguish this session's own claim from foreign work; never clear records from this helper's output. Its snapshot is advisory, not a lease or authority override. Check every prospective experiment root before creating a batch.

For a destination the user will create manually, provide the exact command and verify it exists after their completion message; do not ask them to recreate an already present project folder. Once the root is resolved and preflight permits preparation, call omp_control.workspace_prepare with that canonicalRoot, use it as shell cwd and on project_get/project_register/run_begin, and use absolute file paths. Preparation does not change the native session cwd; verify the actual cwd before native task dispatch. A ROOT_MISMATCH alone is corrected with the known root, not relocation. An empty child under a registered project is not independently registrable; unrelated sibling roots do not overlap. Never move a shell to C: to evade D: occupancy or infer a lock is stale. Old loaded extensions may need a normal settled process restart; /reload-plugins in OMP 18.1.19 does not reload the already-loaded standalone TypeScript controller extension.

For the single-task worktree delivery method, read `~/.omp/agent/notes/worktree-delivery.md` after target and workspace preflight. A linked task worktree must be a direct `D:/OMPData/worktrees` leaf, registered and used from the session's actual moved cwd before controlled author dispatch. It does not grant a fake child cwd, a shared-repository merge lock or permission to bypass an occupied target.

## Occupied parent directory: user-selected independent folder

Standing preference (2026-09-14): on a confirmed foreign parent-directory WORKSPACE_BUSY, ask once whether to create the project in a different, unoccupied D: directory. Propose the exact absolute path OUTSIDE every conflicting root; another child under the occupied parent does not solve the conflict. For example, if D:/projects/omp/project is occupied, consider D:/projects/omp/projects/booking-system only after checking that path and its ancestors. Reuse all accepted scope, depth, design and implementation decisions; ask only about the changed destination. Do not create it before the answer, repeatedly probe the same blocked path, request closure of an active controller, clear its lock or rename/move existing project files. An existing implementation needs an explicit migration decision; this fallback does not authorize discarding its code/history.

The destination question must be concrete and user-facing Chinese: name the project, the proposed folder name, its full absolute path, and briefly explain why this location avoids the occupied directory. Include the proposed path inside the question itself, not only in hidden notes or an earlier status update. Offer confirmation of that exact proposal or a user-specified alternative; never just say "create another folder" or ask the user to invent a name. After checking collisions, propose one sensible project-specific name. Honor the user's latest preference to create the folder manually: provide the exact PowerShell command, starting directory and final destination, followed by the native /move command when needed. Do not leave name/path placeholders or repeatedly ask permission; an explicit request for the agent to create the chosen directory overrides this manual default. This applies to both initial new-project intake and the occupied-parent fallback.

After the new root is confirmed, prepare that exact directory with workspace_prepare. Native OMP 18.1.19 task inherits the actual session cwd and has no per-call cwd field; text inside its assignment and workspace_prepare do not change it. If the current session is still rooted in the occupied container, pause at a settled boundary and show the user the native `/move <confirmed-existing-directory>` command once, substituting the actual confirmed absolute path in a copyable command after the directory exists. Never leave a placeholder for the user to fill in. This changes this session's directory while retaining conversation; it does not move project source. Verify the resulting cwd before ordinary task dispatch and Git initialization. Do not claim a shell-only cwd change moved the session. Do not use a new controlled run just to bypass this preference.

OMP installation/package/runtime source is read-only for this configuration task. Use existing native capabilities and locally maintained instruction files. Do not add a custom dispatch/lock-recovery mechanism or patch native code to avoid this destination choice. ROOT_MISMATCH without an actual occupancy conflict still uses the known canonicalRoot instead of asking for another folder.

## Ordinary workspace recovery

The control extension automatically records root tool writes and ordinary task dispatches, including unregistered workspaces. It retains occupancy while background jobs run and releases it after the completed turn. Controlled dispatches share this registry. This is cooperative OMP coordination, not protection against external editors or arbitrary shell commands targeting undeclared directories. Keep every writer within the explicit cwd/assigned paths; serialize overlapping writes inside one session. Use `workspace_status` to inspect a conflict. Do not close a live controller as a shortcut. After a crashed controller, inspect remaining children and workspace side effects; `workspace_reconcile` accepts the stale token and a JSON payload with `processesStopped: true`, `sideEffectsKnown: true`, and nonempty evidence only after the former controller has stopped. This records recovery; it does not clear unfinished controlled tasks or prove task completion.
