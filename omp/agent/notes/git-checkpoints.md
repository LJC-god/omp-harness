# Automatic local Git baseline and step commits

Standing user preference: apply to assigned native and controlled software work, including frontend projects. Explicit task instructions such as no Git/no commit take precedence. Pure read-only investigation and disposable no-Git fixtures do not create commits. Local history is independent of control-plane baseline_capture and semantic omp_checkpoint; neither replaces a Git commit. This adds no agent, remote publication, approval ceremony or full review gate.

- Before the first assigned project artifact write, resolve the intended root and ancestor Git relationships and existing activity. Sol may run `git init` and create an empty baseline commit because Git ownership is retained; the assigned author creates or updates ignore rules for dependencies/build output/local secrets before adding project files. In a populated non-Git project, inspect the intended source/configuration paths and create an honest current-state baseline before further changes; never invent historical stages. In an existing repository, retain HEAD as the starting baseline and record its SHA plus pre-existing dirty/staged paths in the existing task/checkpoint. Do not commit unrelated user changes to make it clean. An unborn existing repository needs an initial scoped baseline. Follow project branch policy without resetting history.
- Commit after EACH completed, independently verifiable planned implementation step that changes tracked deliverables: for example scaffold, core behavior, UI integration, and a verified repair. A step is a meaningful planned result, not each command, file save, read, test invocation or chat message. A one-step fix needs one implementation commit. Do not defer all milestones to a single final commit, invent retroactive stages, or create empty commits for checks with no changes. New-project baseline creation is the only routine empty-commit exception.
- Sol is the default Git owner. State commit ownership in the ordinary worker assignment. A single exclusive writer may be explicitly authorized to commit its own verified steps inside a multi-step assignment, on the already-established branch and baseline; otherwise it returns to Sol at a planned step boundary before starting the next dependent implementation step. Reviewers never commit. Never allow concurrent writers to race over the shared Git index; serialize checkpoints under the existing ownership/lease discipline rather than adding a manager.
- Before every checkpoint commit, run only verification relevant to that step, inspect the exact diff and index, scan intended content for secrets, and stage explicit task-owned paths. Preserve unrelated staged/unstaged work; do not use blanket git add . or git add -A, reset/stash other work, disable hooks, invent Git identity, or stage dependencies/build artifacts. A baseline snapshot records starting state and does not imply the inherited code has passed tests. If a hook or check changes source, inspect that change and verify the affected behavior before committing. A failed step is not completed; retain its work and diagnosis instead of committing a claimed success.
- Use concise English Conventional Commit messages; record each resulting SHA beside its completed step in the existing plan/checkpoint when one exists. Before the next step or final answer, confirm the prior checkpoint exists and inspect remaining task-owned changes. A lost response requires checking git log/status before retrying; do not create duplicate commits or amend away previous checkpoints. Report an actual identity/hook/ownership failure precisely and continue independent authorized work; never silently omit Git or claim completion while the required checkpoint is missing.
- If unrelated changes are already staged, a plain git commit would include them. Use a reviewed path-scoped `git commit --only -- <owned paths>` only when those whole working-tree paths are authorized and separable; preserve the other index entries. Mixed ownership inside one file requires isolating the authorized change or resolving that actual conflict, not sweeping the file into a commit.
- Controlled runs still perform their baseline_capture and generation/lease checks. Commit step changes before the reviews meant to validate that committed candidate; a changed HEAD invalidates old gate fingerprints, so never relabel an older PASS. Reuse applicable checks already run on unchanged content. Local commits do not authorize pushing, creating remotes, force-pushing, or public publication.
