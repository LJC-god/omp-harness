# Continuity and recovery

Read for multi-phase checkpoints, compaction recovery, cross-session handoff or interrupted work. Small one-step work skips checkpoint ceremony.

Checkpoint size and workflow labels do not grant authorship: all software/product design and development, including small fixes and integration repairs, stay with assigned child agents under main-agent-orchestrator.md. Sol coordinates recovery and judges evidence; it must not resume a worker's unfinished implementation itself. A completed child receipt is only evidence of that attempt, never permission for Sol to author the remaining work. A confirmed post-implementation defect transfers to repair-worker only after the original writer settles; interrupted implementation recovery remains with that original writer. The existing product-only completion floor is not a source-write restriction or proof that this broader ownership policy was followed.

Keep handoffs short: relevant confirmed requirements and their source, current source/owned paths, checks and unresolved work. For a repair or recovery, include the prior failure, corresponding repair diff/source and evidence, and the exact remaining verification; use the compact handoff in verification-evidence.md. Retain the full accepted scope in its owning brief/checkpoint. A worker's PASS is a claim; use current evidence. Research conclusions include sources and uncertainty. Read only relevant logs/notes; reuse unchanged checks and model routes. Keep memory in three existing places: durable project/user facts in the owning project note or long-term memory; current goal, branch, port, role/owner and pending checks in the session checkpoint; experiments, superseded decisions and logs in historical evidence. Never promote temporary runtime/role identity or a single unverified diagnosis to shared long-term memory. Scope project-specific facts to that project. Do not add a memory database or load the archive into every task.

For multi-phase work use the existing `omp_checkpoint update`: goal describes the accepted outcome; constraints and authorizationRefs retain confirmed requirements and message references; completed, failedApproaches and nextAction describe the current execution state. For complex work, requirements maps acceptance to actual evidence. These are existing fields, not a new schema. Give accepted requirements stable labels inside the requirement text (R1, R2, ...), including explicit delivery paths. Scalar fields merge, but supplied arrays REPLACE their previous contents: before sending requirements, constraints or authorizationRefs, read the current checkpoint and retain every still-applicable entry; omit an unchanged array. Never replace the accepted requirement list with only the latest repairs or gates. Use completed/failedApproaches/nextAction for phase progress. The native limits are eight requirements, eight items per constraint/reference list and 600 characters per string; retain larger accepted scope in the existing project brief with labelled references, not by dropping requirements or inventing schema fields. Empty lists clear a field; reset: true is for a genuinely new goal, not every milestone. Before status: complete, compare the FULL accepted list with current artifacts and user messages, including the actual installation/output path; a gate PASS cannot cover an omitted requirement. For product checkpoints, completion also needs a nonempty list whose every requirement is covered and has nonblank evidence. A plain progress update after a changed or unknown source downgrades carried covered requirements to pending; retain their historical references, review the current source, then explicitly resend the full requirement list to claim coverage again. An explicit full list may be supplied with completion on a non-Git/unknown root, but its structure does not prove the evidence truthful, externally available or currently acceptable. Small one-step work needs no checkpoint ceremony. After compaction compare the plan with retained intent and current source; recover ambiguous original messages via the existing history tool before asking the user again. Checkpoints guide navigation, not acceptance or authority transfer to new sessions/forks. For explicitly requested cross-session continuation, use the handoff acceptance in verification-evidence.md: verify the relevant source and execution ownership, then establish the first real action before reporting that work has resumed. Never replay writes, commits or pushes because a response was lost.

For a running controlled task, use `task_observe` with projectId/idempotencyKey, then its returned version and `waitMs: 20000` (maximum 25000). Waiting happens inside the tool; heartbeat-only changes do not wake the model early. On terminal status retrieve `includeResult: true` once; results remain repeatably readable after interruption. Interrupted execution still requires existing recovery checks. This observes existing work, never reserves a future write slot or authorizes a retry. Do useful independent work between waits; do not repeatedly call immediate task_get for unchanged status.

Read durable decisions only when relevant in the existing project ADR/notes or memory. Record verified lasting decisions and explicit stable preferences; update the owning current-state note instead of appending conflicting rules, and keep superseded rationale in history. Include why and evidence; write relevant project notes before final source verification. Read a full existing memory before replacing it; use supported supersession for stale facts when available, not bulk deletion of historical memory. One rule has one authoritative location; other entries use short scoped references. Global OMP rationale remains in `~/.omp/agent/notes/workflow-decisions.md`, consulted only for orchestration changes.


Task health uses real subtask output and tool events, not controller heartbeats. A health stop requests cancellation of the affected task and records its reason; it does not prove child processes or writes have settled. Inspect native task status, retained transcript and affected files before recovery. Never ask the user to close the root session as the default fix, and never blindly replay writes. Quiet active tools retain their native timeout and total task cap. Three identical tool failures without a repair stop that attempt; use a new attempt after checking the cause.

When resuming after a provider error, distinguish a running child, native scheduled retry and a terminated root turn. Read the original terminal error/health record and tell the user the observed cause; a completed child does not mean the parent kept working. A certificate error requires connection/trust diagnosis, not a claim that the task is still running. Keep unknown root causes explicit and resume only the unchecked remainder under existing authorization. The health extension records terminal provider failures without starting another model request.

During long work, give a concise Chinese progress update at meaningful milestones and about every 3-5 minutes when tool boundaries permit: landed result, current obstacle, next check. A long blocking call may prevent an update; explain its result when it returns, without claiming an unseen heartbeat. Native budget notices and forced yields are harness limits, not user cancellation; retain truthful partial state and let Sol assign unsettled remainder. Do not repeatedly promise "the last issue" before acceptance is known. After two unsuccessful repairs of the same boundary, revisit its shared cause and affected callers within existing authorization; this is not another user approval or a reason to waive a blocker.

When diagnosing slow work, read `omp_task_metrics` for observed startup/model/tool/retry time; overlapping child times must not be added as wall time. This is optional diagnostic data, not another completion gate. For long work, record a compact `failedApproaches` entry with cause and evidence when an approach fails. Use `omp_history` with a narrow literal query to recover original current-branch messages before asking the user to repeat earlier decisions. Lookups are reference data; newer user instructions prevail.

## Task accounting and routing feedback

At the start of a complete product/system, set `workflow: "product"` and explicitly set `userFacing` in `omp_checkpoint update`; ordinary work may omit both. New declarations receive the runtime v3 acceptance contract and the checkpoint records the current branch leaf as its task boundary, so earlier child receipts cannot be reused. V3 completion needs a completed implementation child, covered requirements, and runtime-observed current-source PASS receipts: verifier, security-reviewer and purple-reviewer, plus gpt-visual-director and experience-reviewer for user-facing work. Saved v2 and legacy checkpoints retain their prior completion contract and are never retroactively changed. A failed/pending child, a textual PASS, an old controlled observation, a running or invalid same-role review, or source drift is insufficient. Reset is only for a genuinely new user goal, never an escape from missing evidence; resetting an active product requires a newer user message, and any new product declaration captures applicability again.

Use the existing checkpoint to define a major task's boundary: create/update it when starting multi-step or delegated work, reset only for a genuinely new goal, and set status complete after reconciling the full accepted scope with delivered artifacts. Intermediate milestones and a worker/gate PASS are not task completion. The task-usage extension automatically appends one recorded per-model usage table after the root finishes its final response. No extra model request or user approval is needed. Do not manually invent token counts or duplicate the automatic table. Use omp_usage_report only for an on-demand snapshot or to recover an unavailable footer; it does not complete the task.

Accounting follows the current task window on the selected native session branch and referenced child transcripts, including recorded failed attempts, actual fallback models and auxiliary model_usage records. Show input/output/cache tokens, recorded model-request time and separate whole-task elapsed time (including tools and waits). Never add parallel/model times as wall time or translate subscription usage into a money bill. Missing usage/time stays explicitly partial; this is not all-account or cross-session billing. After a cross-session handoff, report only the receiving session's recorded scope, with previous-session evidence separate. Existing tasks without a tracked start may produce a partial window. The footer is descriptive evidence, not a completion gate or product PASS.

For later routing decisions, use time to accepted delivery, repair causes/counts from existing failedApproaches, and original-requirement coverage. Do not add another mandatory evaluator or repeated benchmark to every task. Available quota alone is not evidence of better speed. Keep Grok assignments bounded with a concrete stop condition and handoff time; preserve author-owned checks/repairs. Luna's configured effort does not expand its mechanical responsibility.

## Cross-session handoff acceptance

When the user explicitly requests saving or resuming work across sessions, use the existing project brief/state record and checkpoint references; do not automatically create another session, reminder hook or parallel state file. Retain the exact root, source/commit and uncommitted changes, relevant accepted requirements and their provenance, checked versus unchecked work, known failed routes, live task/process ownership and one concrete next action with its verification. Read the current record before updating it; preserve other owners' changes and keep credentials out.

The receiving session checks only facts needed for that next action against actual files and task state. Treat old notes as reference, never as fresh authorization or proof of PASS. Before writing, establish that the previous writer has settled and the receiving session is allowed to own the scope. A controlled run remains bound to its original owner; a handoff cannot transfer run identity, settle uncertain execution or evade leases. Resume the original owning session or resolve the actual conflict through existing controls. Do not replay a possibly completed write or create a duplicate task because a response was lost.

Distinguish saved material, created session, verified receipt and resumed work in the existing handoff text. Only report work resumed after the receiver has performed the first real action (an executed inspection/check or authorized change) and retained its result/source; an acknowledgement or plan alone is insufficient. The outgoing session stops writing when an authorized handoff gives the receiving session that scope; uncertainty about delivery means inspect ownership, not write from both sides. Direct user instructions to continue with clear scope need no extra confirmation round. Missing tools or critical evidence produce a precise remaining gap, not a fabricated successful transfer.
